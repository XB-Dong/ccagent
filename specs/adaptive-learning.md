# 反馈、记忆与 Skill 自适应机制

版本：0.1.0｜状态：P0 设计提案，未实现

执行更新（2026-10-26）：实现已开始，当前约束见 [运行契约 v0.2](contracts/runtime-v0.2.md)；来源/精确归并、结构化纠正、摘要、L0 内部清单重放、Skill Provider、撤销和删除账本已有离线证据，完整验收仍进行中。保留下文目标与设计边界，不把已写代码等同全部通过。

对应 CC-FEEDBACK-001、CC-MEMORY-001、CC-SKILL-001、CC-HISTORY-001。[业务原意](../docs/product/REQUIREMENTS.zh.md)与实现政策分开；本稿的触发次数、启用门槛和保留策略需 R0 定稿。

## 1. 四种不同工件

| 工件 | 保存什么 | 可以做什么 |
| --- | --- | --- |
| 原生会话压缩 | 模型上下文的短摘要及上游事件引用 | 继续对话，不自动证明业务规则正确 |
| 业务记忆 | cc 确认的偏好/事实、范围、来源、时效 | 给后续任务提供受范围约束的背景 |
| 迭代反馈 | 不满意、纠正、功能建议、影响、期望/实际 | 形成候选需求，关联后续开发与验收 |
| Skill | 可复用流程、前提、步骤、校验和失败处理 | 在已有工具权限内指导完成任务 |

研发 Agent 的规则、记忆与交接存在代码库；cc 运行时的以上工件在业务存储。自动学习不能编辑 AGENTS.md、CONSTITUTION.md、源码、部署配置或凭据。

## 2. 自动捕获与归并

触发：cc 明确点击反馈、自然语言表达不满/纠正、cc 确认某任务结果或流程成功。显式入口先用确定性代码保存原始事实，自然语言提取由模型辅助。

模型提取结构化候选并引用 source event/message ID；服务端校验引用确实存在、属于当前范围和可读取内容。没有来源的输出进入拒绝/待澄清队列，不伪装成 cc 确认。

候选含 `observation / preference / correction / improvement / workflow` 类型，以及期望、实际、场景、影响和确认状态。含糊的“这不行”可先捕获，随后补充上下文。抱怨不自动变成流程步骤；“我试试这样”不等于成功经验。

相同来源事件重复消费完全幂等。语义相似只提出可解释归并，保留各自证据与频次；互相冲突的要求不合并。无需一开始引入 embedding/向量库，先按类型、页面、实体和范围检索，再在有限候选内辅助归并。

## 3. 压缩与上下文装配

会话压力压缩复用原生 seam；业务记忆按完成任务、事件增量与可配置体积触发整理。启动建议 `learning.enabled=true`、单学习 worker、有界队列，触发与 token 预算在 R0 通过合成用例决定，不声称用户已指定固定阈值。

结构化字段和 provenance 是权威，摘要是可重建投影。压缩保留确认事实、待确认、冲突、有效范围、截止/时间单位、原始证据 ID、被替代/撤回关系；不能只留“最终结论”而丢掉约束。关键金额、数量、币种与时间按结构化原值保存，摘要不能改写。

发布摘要前检查 schema、来源闭包、范围、冲突和关键字段一致性；失败保留旧摘要和待处理增量。并发压缩使用 revision/CAS，只有引用范围未变化才更新。源事件归档/删除遵循独立保留策略，不因摘要成功就自动删除。

下一会话只装配当前 owner/workspace、店铺/站点、有效期和任务相关的有限记忆；被撤回、不再有效或未确认的推断不得作为已确认规则注入。新纠正更高优先，但保留旧记录与替代依据。跨店铺迁移经验须显式泛化确认。

## 4. Skill 自动提炼与发布

```text
确认成功的任务/流程
  → 自动生成 candidate
  → 结构/权限/范围/来源检查
  → 合成场景 dry-run 和预期结果校验
  → validated
  → 低风险按策略自动 active；其余 waiting_confirmation
  → 监测失败/纠正 → suspended / superseded / revoked
```

提炼触发建议：一次 cc 明确说“记住这个流程”即可生成候选；普通重复流程可在两次已确认成功后自动提炼。次数是可配置设计值，尚待 R0 评估；任何候选不因生成成功就自动算 `validated`。

Skill 需要 `name/version/description`、适用范围、输入 schema、前置条件、有序步骤、预期结果、失败处理、工具白名单、风险等级、来源、验证结果、作者/生成模型、替代关系与内容哈希。上游模型可见目录只投影必要的 name/description，不把业务原文或全量记忆塞入系统提示。

启用分级提案：

| 类别 | 例子 | 规则 |
| --- | --- | --- |
| L0 只读解释/内部草稿 | 整理活动准备清单、汇总已有任务 | 确认来源、规则通过、合成回放成功、范围未扩大后可自动启用 |
| L1 业务计划变更 | 调整预测假设、重排发货计划 | cc 确认该版本后启用；具体任务仍按工具权限执行 |
| L2 外部副作用 | Amazon/ERP 建单、改价、改广告、发消息 | P0 禁止执行；后续每次操作另有授权与幂等/恢复设计 |

通过专用 `cc-approved` Skill Provider 发布经过状态检查的版本；草稿与撤销版本不能被上游默认 filesystem 扫描到。名称用上游支持的 kebab-case，防止与系统 Skill 冲突；业务权限由服务端强制，不依赖正文声明。Provider 要校验 scope、状态和哈希，状态变化主动失效缓存。

已开始的任务记录使用的 Skill 版本快照。执行每个实际工具前再次检查撤销状态和权限；撤销后未发生的副作用被阻止，在途副作用进入核查/补偿，不能谎称自动撤回。新会话不再发现已撤销版本；旧会话里的文本也不能恢复其权限。

## 5. 纠正、删除与隐私

cc 可以查看来源、纠正、停止学习、删除某条记忆/反馈/Skill。学习开关关闭后不再派生新候选，已经运行的学习任务可取消；基础操作正常。模型不可用时事实仍先落盘，队列可见地等待，不丢数据。

删除时使相关摘要、候选和 Skill 失效并重建受影响投影，阻止任务重试从旧缓存重新生成。业务库保留最小撤销/删除标记而不保留被删原文。会话、附件、备份的删除范围与保留期必须可说明；备份恢复后先应用删除/撤销账本再开放服务。合规保留策略尚待确认，不承诺所有备份即时物理删除。

外部文件/网页指令不能成为可执行 Skill。凭据、Cookie、客户个人信息和未经允许的公司数据在模型请求与日志前过滤/阻断；模型用量日志只记录脱敏 metadata。正式数据流经用户确认后再启用；P0 使用合成数据验证。

## 6. 反馈到按日需求记录

产品自动维护业务库中的 Feedback 和候选 RequirementChange，cc 可看见“已记下，待归类/确认”。确认后生成仓库外脱敏审阅包：稳定需求 ID、日期、原意、变化前后、理由、来源引用和确认人。

研发侧在用户授权的需求更新任务中，把审阅包按[追加约定](../docs/product/changes/README.md)写入当日文件并同步业务总览。产品本身不持有 GitHub Token，不自动推送或启动开发。导出使用稳定 changeId，重复导出/导入不重复追加。

## 7. 效果衡量

记录反馈捕获完整率（以人工标注合成集为分母）、归并误差、来源可追踪率、压缩关键字段保真率、检索范围违规次数、Skill 实际成功率/修正率，以及学习耗时/token。P0 的硬门槛是关键合成案例全部满足不丢纠正、不串范围、不越权和可撤销；不编造尚未测得的生产准确率。
