# 同类项目调研与技术迁移建议

日期：2026-10-26｜范围：用户提供的六个项目；只读调研，未运行、安装或接入任何服务

目的：补强 cc 的原有运营需求，筛选可迁移的设计和依赖；不把六套应用拼成新底座。ccagent 继续使用官方 DeepSeek Harness，当前 P0 范围不扩张。源码基线和所读文件见[来源索引](operations-source-index.json)，业务候选见[需求文档](../product/REQUIREMENTS.zh.md)。以下“推荐”是本项目的评估，不表示参考项目已在真实业务中通过验证。

## 2. FBA / AWD 看板：借展示和 CSV 工具，不借补货公式

读取 README、`js/app.js` 和 MIT LICENSE。该项目能在浏览器读取 CSV，按位置展示库存和图表；实现中按 SKU 合并报告，并使用覆盖天数状态。[固定版本源码](https://github.com/BWB03/inventory-dashboard/blob/34d517a3150e1caa888dbd05767f419c9b9d3d53/js/app.js)。

- **PapaParse**：适合作为 CSV 浏览器预览/字段映射的候选，支持逐步或分块解析；SKU 等标识按字符串处理，不盲开数值推断。服务端仍做权威校验，浏览器解析不能替代持久化与口径校验。[官方文档](https://www.papaparse.com/docs)
- **Chart.js**：适合基础库存分布、销量趋势和库存预测线的候选，具有 TypeScript 类型且可与 React 集成；先检查 Harness 现有可复用组件，再决定是否引入，避免同时堆多套图表库。[官方文档](https://www.chartjs.org/docs/latest/)
- 页面借鉴按位置/状态展示，适用 AWD/3PL 与否取决于 cc 是否实际使用。
- 不直接迁移“库存相加 + 覆盖天数”的补货逻辑。仍按店铺/站点/商品身份、快照时间、库存状态、预计到货和共享批次分配推演每日库存，避免同一批货重复计入。

## 3. 销量预测：借回测和场景，不默认上六模型

读取 README、forecast_engine 与 inventory_recommender。该项目有简单加权基线、统计/机器学习候选、滚动回测、补货与场景比较；README 同时说明主要为合成数据验证，区间校准及测试覆盖有限。[固定版本 README](https://github.com/La0310/timeseries_stock_forecasting/blob/e97727813204ab9f59db99f849e1ade25c176b7d/README.md)。

- 先迁移“**简单基线 → 时间顺序回测 → 解释误差与适用条件**”的方法，可先用 TypeScript 实现轻量规则，不为模型数量增加复杂度。
- 数据量和真实回测证明有价值后，再评估 **pandas/NumPy/statsmodels**；LightGBM 不作为初期默认依赖。可通过有界分析任务集成，不强制复制 FastAPI + SQLAlchemy 服务架构。
- 回测只使用预测时点之前的数据。稀疏/零销量、断货导致销量受限、活动和历史不足要分开；不能把未来信息或库存为零误当成真实零需求。
- 高/中/低场景初期只是显式假设，不冒充经过校准的概率区间。预测周期、安全库存服务水平、类别阈值、箱规/MOQ 都以 cc 实际业务为准，不抄固定 28 天、95% 或演示类别常量。
- 当前所读树未观察到 LICENSE 文件；本轮只借鉴思路。若要复制源码，先核实授权，不能因 GitHub 可读就当作可自由复用。

## 4. LLM 表格分析：借受控计算与结果结构，保留 Harness

读取 README、requirements 以及 `core/tools.py / dataset.py / experience.py`。值得借鉴的是模型组织工具、程序计算数字、工具输出表格/图表、记录反馈和用量。[固定版本源码](https://github.com/quguolin/llm-data-agent/blob/f5732b8afb2bafbb9eacfcce3ed692c4dfca2ee0/core/tools.py)。

- 后续 Excel/CSV 分析可评估 **pandas + openpyxl**，导出 Excel 再评估 **xlsxwriter**；只引入实际需要的格式和依赖。[pandas I/O 官方文档](https://pandas.pydata.org/docs/user_guide/io.html)
- 在 Harness 中注册列举、筛选、分组、趋势、差异比较等**明确参数的只读工具**，返回数据集版本、筛选、口径、单位、结果与警告；不让模型心算库存或广告指标。
- 不迁移 openai-agents/LiteLLM 编排层、Streamlit 整站或完整请求日志；它们会与当前 Harness/Web UI 重复。
- 不能照抄 README 的绝对隐私保证：所读实现会输出列取值/样本文本，`execute_pandas_code` 使用字符串黑名单与 Python `exec`，不构成可靠沙盒。ccagent 不开放该任意代码入口；发往模型的摘要/样本同样需要权限与脱敏校验。
- 不把“继续追问/一句嗯”等自动当成成功证明，也不因节省上下文丢弃 cc 的否定与纠正。延续本项目的确认、来源、范围、撤销和 Skill 验证机制。
- 该项目的“本地”不能直接照搬为“数据不离开 cc 电脑”：若计算部署在云主机，文件上传已是一次数据传输，仍需明确许可。

## 5. 库存分析：借数据健康与风险优先级

读取 README、requirements、`src/validate.py / identity.py / restock.py` 和 MIT LICENSE。[固定版本源码](https://github.com/Rohit-Punjabi/inventory-analytics-dashboard/blob/3dc5c375ae3c2a8889621d61eba7bcb2b0d5d6a2/src/validate.py)。

- 借鉴导入后的质量面板：缺字段/缺日期、异常数量、身份映射、期初/收发/期末核对与来源追踪。严重错误阻止发布依赖它的建议；有足够依据的其他独立分析可继续。
- 该项目按服装款号归并名称，ccagent 应按店铺/站点与 SKU/ASIN/FNSKU 建立经确认的映射，不能借正则把亚马逊变体、不同店铺同 SKU 直接合并。
- 借鉴缺货风险、积压、周转和待补货列表；每个状态都能下钻到原因、源快照和影响范围。
- 其主要粒度是月度，restock 公式使用月数；不能当作 cc 要求的每日入仓/缺货推演。退货、调拨、损耗和调整需按真实台账解释，不能用简化守恒式把不完整账目硬判成错误。
- 候选依赖为 pandas/openpyxl 与有必要时的 statsmodels；Streamlit、PyInstaller/Windows 壳、Plotly 整套界面不搬入当前 React 工作台。

## 6. Amazon 接入：SDK 与托管 MCP 分开评估

**python-amazon-sp-api**：读取 README、MIT LICENSE 和 Reports 客户端源码。它是第三方对官方 Selling Partner API 的封装，可作为后续只读库存/销售/报告适配器候选；报表是请求、等待处理、下载、校验的流程，不是假定每次请求立即拿到最新数据。[固定版本 README](https://github.com/saleweaver/python-amazon-sp-api/blob/b19785afa8df885af045337f877dd2bd54c87ab6/README.md)、[Amazon Reports 官方说明](https://developer-docs.amazon.com/sp-api/docs/reports-api-v2021-06-30-use-case-guide)。

接入前核实卖家授权、marketplace、角色权限、分页、限流、报表时效和版本；SDK 不替代授权。库存各状态按[官方 FBA Inventory 定义](https://developer-docs.amazon.com/sp-api/docs/fba-inventory-api-v1-use-case-guide)分别记录，不把总量一律视为可售。广告数据另评估 **Amazon Ads API** 的申请/授权与报表，不能认为 SP-API Key 已覆盖广告。[Amazon Ads 官方说明](https://advertising.amazon.com/about-api)

**Propamp MCP**：当前固定树只有 README，介绍的是需要其平台账号与卖家连接的托管服务，声明 Proprietary；其工具数、范围和服务效果为文档声明，本轮未实测。[固定版本说明](https://github.com/PropampAI/Propamp.ai-for-Amazon-Sellers-MCP/blob/d277825c8c04d84b927e55b07f609a69a0944fcd/README.md)。因此只参考工具分组、最小只读权限、数据范围与撤销机制，不将其列为可自部署开源模块、不注册或授权账号、不自动传数据。若未来确有购买/使用意愿，另评估服务条款、许可、成本、数据去向和实际可用性。

## 7. 迁移路线与边界

| 层 | 当前保留 | 后续可评估的迁移部分 | 暂不引入 |
| --- | --- | --- | --- |
| 运行框架 | DeepSeek Harness + Node.js/TypeScript | 受控工具与业务插件组织 | 第二套 Agent runtime、多模型网关 |
| UI | React、上游主题/CSS Modules | CSV 预览、Chart.js 基础图、质量/风险列表 | Streamlit 整站、另一套桌面客户端 |
| 数据/算法 | P0 业务 SQLite 提案、确定性规则 | pandas/openpyxl、简单预测与按需 statsmodels | 全量六模型训练、常驻重分析平台 |
| 外部适配 | 初期报表手工导入方向 | python-amazon-sp-api 候选、独立 Ads 数据适配 | 未授权外部写入、默认购买 Propamp |
| 存储 | 原生会话 + 业务库 + 受控文件目录 | 数据批次/映射/分析快照与缓存失效设计 | 向量库、Redis、对象存储集群作为初期必选 |

先沉淀需求与数据契约；数据接入/库存/广告波次按实际样表、资源与授权选择依赖，并锁版本、保留许可证及补足测试。采纳设计不等于已经引入源码或扩大本轮开发范围。本次 DeepSeek 调用为 0。
